# Чек-лист безопасной установки Enforce 2SV на Jira DC (прод, без тестового стенда)

Плагин по умолчанию собран в безопасном состоянии: `enforce2sv.dryRun=true` (только логирует,
никого не редиректит) и fail-open при недоступности БД. Это сделано намеренно под сценарий
"ставим сразу на прод". Тем не менее ниже — план, снижающий риск самой установки OSGi-бандла.

## Проверено на локальном инстансе Jira 10.6.1 (14.07.2026)

Полный цикл подтверждён вживую: dry-run логирование, блокирующий redirect
(302 → `/secure/ViewProfile.jspa`), отсутствие redirect-loop, переключение режимов через REST
без рестарта, fail-open при ошибке БД. Ключевые уроки, уже отражённые в коде:

- **DI**: Spring Scanner (constructor injection) в этой сборке Jira работал ненадёжно — плагин
  полностью переведён на `ComponentAccessor` + ручное создание зависимостей в `Filter.init()`.
  Не возвращать @Inject/@ComponentImport без стенда для проверки.
- **SQL**: имена AO-таблиц/колонок в PostgreSQL обязаны быть в двойных кавычках
  (`"AO_ED669C_TOTP_USER_ENROLLMENT"`), иначе `relation does not exist`.
- **Страница 2SV в Jira** — это панель на `/secure/ViewProfile.jspa` (view-profile-panel из
  atlassian-authentication-plugin), отдельного URL нет. `/plugins/servlet/two-step-verification`
  существует только в Bitbucket/Bamboo/Crowd.
- **Логирование**: если Root-логгер = WARN (типично для прода), INFO-логи `[ENFORCE_2SV]` не
  попадут в файл. Добавить в log4j2.xml (через Admin → Logging and Profiling, runtime, или в
  конфиг): `<Logger name="com.internal.jira.enforce2sv" level="INFO" additivity="false">
  <AppenderRef ref="filelog"/></Logger>`.
- **`OfBizConnectionFactory`** — PICO-компонент jira-core: получать через
  `ComponentAccessor.getComponent(...)`, НЕ `getOSGiComponentInstanceOfType(...)` (вернёт null).

## 0. Перед установкой

- [ ] Выполнить `scripts/diagnose-2sv-table.sql` (read-only) и подтвердить реальное имя
      AO-таблицы/колонки. Таблица/колонка (`AO_ED669C_TOTP_USER_ENROLLMENT`/`USER_KEY`) уже
      подтверждены на проде 14.07.2026 — перепроверить только если Jira патчилась.
- [ ] Убедиться, что `enforce2sv.dryRun` действительно `true` (это дефолт, но проверить явно
      через `GET /rest/enforce2sv/1.0/config` после установки).
- [ ] Настроить логгер `com.internal.jira.enforce2sv` = INFO (см. урок выше), иначе dry-run
      будет "слепым".
- [ ] Выбрать окно с минимальной нагрузкой (не пиковые часы).
- [ ] Сообщить дежурной смене/себе, что в ближайшие N минут возможен plugin reload на нодах.

## 1. Установка (staggered — по одной ноде, если возможно)

- [ ] Скопировать `target/jira-enforce-2sv-plugin-1.0.0-SNAPSHOT.jar` в общий plugin storage
      (shared home / `<jira-home>/plugins/installed-plugins`, согласно вашей схеме NFS).
- [ ] Установить через **UPM (Manage Apps → Upload app)** на одной ноде — плагин реплицируется
      на остальные ноды кластера через shared home автоматически (NFR-9 ТЗ), ручной копии на
      каждую ноду не требуется.
- [ ] Проверить в UPM, что плагин `Enabled` и модули (`enforce2sv-filter`, `enforce2sv-rest`)
      активны на **каждой** ноде (UPM показывает статус кластерно, но стоит перепроверить логи
      каждой ноды на предмет ошибок инициализации Spring/OSGi).

## 2. Первая проверка (dry-run, минуты 0-15)

- [ ] Залогиниться под собственным тестовым аккаунтом, походить по интерфейсу.
- [ ] В логе (`atlassian-jira.log` или где сконфигурирован SLF4J/log4j2) найти маркер
      `[ENFORCE_2SV]` — убедиться, что фильтр реально срабатывает и пишет по ожидаемым URI,
      без exception'ов, без WARN/ERROR о недоступности БД.
- [ ] Убедиться, что задержка страниц не выросла заметно (NFR-1 — не более 20 мс P95;
      на глаз через обычную навигацию, без нагрузочного стенда это не измерить точно,
      но явный "тормоз" будет заметен сразу).

## 3. Наблюдение в dry-run (согласно риску из ТЗ — 2-3 дня перед блокировкой)

- [ ] Ежедневно грепать логи по маркеру `[ENFORCE_2SV]` и смотреть, для каких URI
      `redirected=true` (то есть в реальном режиме случился бы редирект) — это и есть
      кандидаты на allowlist, если они системные/технические, а не "рабочие" экраны.
- [ ] Проверить количество уникальных пользователей с `enrolled=false` — совпадает ли
      порядок величины с ожиданиями (если "почти все = false" при том что часть пользователей
      точно настроила 2SV — вероятно, неверно имя таблицы/колонки, вернуться к шагу 0).
- [ ] Убедиться, что ни разу не залогирован fail-open по ERROR (недоступность БД) — если
      залогирован, разобраться, не связано ли с реальным инцидентом Patroni.

## 4. Включение блокировки (только после dry-run и точечно)

- [ ] Через `PUT /rest/enforce2sv/1.0/config` (только SYSTEM_ADMIN) выставить bypass-группу
      `2fa-bypass-emergency` = **все, кроме одного тестового пользователя** (временно, через
      штатное управление группами Jira).
- [ ] Выставить `dryRun=false` только сейчас, не раньше.
- [ ] Тестовый пользователь: подтвердить редирект на страницу настройки 2SV, пройти настройку,
      подтвердить, что после регистрации редирект прекращается (кеш сессии TTL — либо ждать
      истечения TTL, либо перелогиниться).
- [ ] Прогнать сценарий "выхожу из системы / логинюсь заново" — убедиться, что нет
      redirect-loop на `/login.jsp` и `/secure/Logout`.

## 5. Постепенный rollout

- [ ] Расширять исключение группами/отделами постепенно (как в п.6 вашего ТЗ), не выключать
      `dryRun` глобально одним шагом на всю компанию.

## План отката (в любой момент)

- [ ] Быстрый откат без блокировки пользователей: `PUT /rest/enforce2sv/1.0/config` с
      `{"dryRun": true}` — мгновенно возвращает плагин в режим наблюдения без переустановки.
- [ ] Полный откат: UPM → Manage Apps → Enforce 2SV → **Disable** (не требует рестарта ноды).
- [ ] Крайний случай: удалить jar из shared plugin storage и выполнить `Uninstall` через UPM.
